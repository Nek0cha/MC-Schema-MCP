# 設計書: テクスチャ付き 3D プレビューと AI 向けの画像レンダリング

- 日付: 2026-11-08
- ステータス: ユーザー確認待ち
- 位置づけ: 改善ロードマップ 4 段階のうち第 3 段階。第 1 段階（チャンク型の保存）と第 2 段階（編集ツール、接続判定の修正）を前提にする。

## 背景・目的

現在のプレビューは、Y 層を 1 枚ずつ色分けして表示する 2D ビューアである。建物の立体的な形、屋根やシルエット、街全体の配置が分かりにくい。また、AI（LLM）はプレビューを一切見られないため、自分の作ったものの見た目を確かめて直すことができない。

本段階では次の 2 つを作る。

1. **ブラウザ用の 3D ビューア**：本物のテクスチャとブロックモデルで描画し、マウスで外から回して眺められる。
2. **`renderView` ツール**：同じビューアを PC に入っているブラウザでヘッドレスに開いて撮影し、画像を MCP のツール結果として AI に返す。描画の仕組みは 1 つだけにして、ブラウザ用と AI 用で共用する（ユーザーの決定：AI も見られるようにする）。

## ゴール

- 500×80×500 規模のマップを、普通の PC のブラウザで回して眺められる（初回の表示まで 15 秒以内、操作中はおおむね 30fps 以上を目安とする）。
- 視点のプリセット（真上、斜め上 4 方向、東西南北の真横）と、マウスによる回転、パン、ズームができる。
- 「この高さより上を描かない」断面スライダーで、屋根を外した状態で斜め上から屋内を見られる。
- ブロックは、client.jar のモデル定義とテクスチャどおりの形と見た目で描かれる（階段、ハーフブロック、フェンス、ガラス板、扉、トラップドアなど）。孤立したガラス板も、ゲームと同じく細い柱として見える。
- ブロックにマウスを乗せると座標と ID が出る。クリックすると座標をクリップボードにコピーする（2D ビューアと同等）。
- プロジェクトを変更すると、変わったチャンクだけが数秒以内に表示へ反映される（リロード不要）。
- `renderView` で、指定した視点、範囲、断面の PNG 画像を AI が受け取れる。
- 既存の 2D の層表示は残す。

## 非ゴール

- 一人称で歩き回る視点（ユーザーの決定：外から眺めるだけ）。
- 本物の光の計算（ブロックの明るさ、影、アンビエントオクルージョン）。面の向きによる固定の陰影だけを付ける。
- ブロックエンティティの本格的な描画（チェスト、看板、ベッド、旗、頭、シュルカーボックスなど。モデル定義がない、あるいは `builtin/entity` のもの）。代わりの箱で描く。
- アニメーションするテクスチャ（最初のフレームだけを使う）。
- バイオームによる色の違い（草、葉、水は平原の固定色で着色する）。
- 第 4 段階のマーカー（スポーン地点、箱の位置など）の重ね表示。ただし、後から重ねられるように、描画にオーバーレイの層を用意しておく。
- client.jar やテクスチャの再配布。キャッシュはユーザーの PC の中だけで使う。

## アンチゴール

- テクスチャを取得できない（オフライン、ダウンロードに失敗した）ときに、プレビュー自体が開けなくなる。その場合は、既存の色分け（`block-colors.ts`）の箱で描くようにする。
- `renderView` が、ビューアの描画が終わる前の不完全な画像を返す。
- 大きなマップでブラウザが固まる、またはメモリ不足で落ちる。
- Edge または Chrome が見つからないときに、エラーの理由が分からない。

## 設計

### 0. 座標と向きの約束

- Minecraft の座標系に合わせる。+X が東、−Z が北、+Y が上。three.js でもこの座標をそのまま使い、カメラの上方向は常に +Y とする。
- 視点プリセットの `north` は「北側（−Z 側）にカメラを置いて、南（+Z）を向く」視点である。このとき、画面の左に東（+X）が来る。`south` はその逆で、画面の右に東が来る。`top` は真上から見下ろし、画面の上を北、右を東とする（地図と同じ向き）。
- 東西を取り違えるとスクリーンショットが鏡像になるので、このプリセットの向きはテストで固定する（§8）。

### 1. アセットの取得とキャッシュ（`src/preview/assets/`）

- **再配布しない**：jar から取り出したテクスチャやモデルを、リポジトリやテストのフィクスチャに入れない。テストは、すべて自作の小さな PNG と JSON のフィクスチャで行う。

- **バージョン**：既定は `1.21.11`（`DATA_VERSION = 4671` に対応するもの）。環境変数 `MC_SCHEMA_ASSET_VERSION` で変更できる。第 4 段階で 1.21.1 向けの書き出しを作るときに、プレビューもそれに合わせて切り替えられるようにするためである。
- **取得の流れ**：
  1. `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json` から、指定バージョンのメタデータの URL を得る。
  2. メタデータの `downloads.client` から、client.jar の URL と sha1 を得る。
  3. jar をダウンロードして、sha1 を照合する。
  4. jar から `assets/minecraft/blockstates/*.json`、`assets/minecraft/models/block/*.json`、`assets/minecraft/textures/block/*.png`（`.png.mcmeta` は使わない）、`assets/minecraft/textures/colormap/*.png` を取り出して、キャッシュに書き出す。
  5. 書き出しが全部終わったら、完了の印のファイル（`.complete`）を置く。jar 本体はキャッシュに残さない。
- **キャッシュの場所**：環境変数 `MC_SCHEMA_CACHE_DIR`、なければ `./cache`。その下に `assets/<version>/`。`.gitignore` に `cache/` を追加する。
- **きっかけ**：`previewBuild` か `renderView` が初めて呼ばれたときに、バックグラウンドで取得を始める。ツール自体は取得の完了を待たない。ただし `renderView` は、テクスチャの取得中であれば最大 120 秒まで待つ。それを過ぎたら、色分けの箱で描いた画像を返し、その旨をテキストで添える。
- **失敗したとき**：失敗の理由を覚えておき、ビューアの画面と `renderView` の結果にテキストで出す。次に `previewBuild` か `renderView` が呼ばれたら、もう一度取得を試みる。
- **依存ライブラリ**：zip の展開に `fflate` を追加する（Node に標準の zip 展開機能がないため）。

### 2. ブロックモデルの解決（`src/preview/models/`、Node 側）

ブロック状態を、描画用の「焼き込み済みの四角形（クアッド）のリスト」に変換する。純粋な関数として作り、vitest でテストする。

- **ブロック状態の定義（blockstates）**：
  - `variants`：プロパティの文字列（`facing=east,half=bottom` など）で一致させる。プロパティの順序と、指定されていないプロパティは無視する（本家の照合と同じ考え方）。候補が配列のときは、先頭を使う（重み付きの抽選はしない。毎回同じ見た目になるようにするため）。
  - `multipart`：`when` の条件（`OR`、`AND`、値の `|` 区切り）を評価して、当てはまる部品を全部重ねる。
- **モデル**：`parent` を親までたどり、`textures` の変数（`#side` など）を解決し、`elements` を引き継ぐ。`elements` の `from`/`to`、`faces` の `uv`、`rotation`（UV の回転）、`cullface`、`tintindex`、要素の `rotation`（軸、角度、`rescale`）を扱う。
- **バリアントの回転**：`x`、`y`（90 度単位）を適用する。`uvlock` は、上面と下面の UV を回転に合わせて補正する程度の近似でよい。
- **焼き込み結果**：`BakedQuad { positions: 4 頂点 (0〜1 のブロック内座標), uv: 4 頂点, texture: string (例 "block/oak_planks"), tint: 'none' | 'grass' | 'foliage' | 'water' | 'redstone' | ..., cullface?: 'north'|...|'down', shade: boolean }`。さらに、ブロックごとに「6 面それぞれが完全に不透明な面で覆われているか」の情報を持つ。これは、隣のブロックの面を省略するかどうかの判定に使う。
- **透明度の分類**：ブロックごとに `opaque`（不透明）、`cutout`（ガラス、葉、草花など。アルファで抜く）、`translucent`（色付きガラス、氷、水、スライムなど）のどれかに分類する。分類は、ID のパターンの表で決める（モデル定義には描画の種類の情報がない、または不十分なため）。
- **モデルがないブロック**：
  - 空気は描かない。
  - 水と溶岩は、`water_still` / `lava_still` のテクスチャで、高さ 14/16 の箱（水は半透明で、水の色で着色）。
  - `builtin/entity` などモデル定義がないもの（チェスト、看板、ベッド、旗、頭、シュルカーボックスなど）は、パーティクル用のテクスチャ（`particle`）で、ブロックより一回り小さい箱にする。テクスチャがなければ、色分けの箱にする。
  - 解決できないブロック（ID の誤りなど）は、マゼンタと黒の市松模様の箱で描く。ビューアの画面の隅に「解決できなかった ID の一覧」を出す。AI が間違った ID に気づけるようにするためである。
- **接続**：サーバーは、第 2 段階で修正した接続の規則を適用したあとのブロック状態でモデルを解決する。こうすれば、フェンスやガラス板の繋がり方が書き出し結果と一致する。プロジェクト全体を毎回なめずに済むよう、`connections.ts` に 1 ブロック単位の関数 `resolveConnectionAt(project, pos): BlockState | undefined`（接続系のブロックでなければ `undefined`）を追加する。既存の `resolveConnections` は、この関数を使って書き直す（結果は変えない）。
- **キャッシュ**：同じブロック状態の文字列の解決結果は、プロセスの中でキャッシュする。

### 3. サーバーの API（`src/preview/server.ts` を拡張）

既存の `/`（2D ビューア）は `/2d` に移し、`/` を 3D ビューアにする。2D ビューアの中身は変えない。

| エンドポイント | 内容 |
|---|---|
| `GET /` | 3D ビューアの HTML |
| `GET /2d` | 既存の 2D ビューア |
| `GET /api/build` | 既存のまま（2D ビューア用） |
| `GET /api/status?project=` | `{ project, revision, bounds, assets: { state: 'missing'|'downloading'|'ready'|'failed', version, error? } }` |
| `GET /api/palette?project=` | プロジェクトのパレットの各番号について、焼き込み済みのモデル（`BakedModel`）、透明度の分類、色分けの色。接続の解決で増えたブロック状態も含める |
| `GET /api/chunks?project=&since=<revision>` | `since` 以降に変わったチャンクのバイナリ。形式は下記 |
| `GET /assets/<version>/textures/...png` | キャッシュしたテクスチャ |
| `GET /vendor/three.module.js` など | `node_modules/three` から配信する（CDN に頼らない） |
| `GET /client/*.js` | ビューアのスクリプト（下記） |

- **リビジョン**：`BuildProject` に、変更のたびに増える `revision` と、チャンクごとの「最後に変わったリビジョン」を持たせる（メモリ上だけでよく、ディスクには保存しない）。読み込み直後は全チャンクのリビジョンを 1 とする。永続化用の dirty の集合（`getDirtyChunkKeys` / `clearDirty`）は保存処理が消費するので、プレビューでは使わない。`setBlock` / `removeBlock` の中で上げるので、第 2 段階の範囲操作やテンプレート配置でも自動的に上がる。空になって削除されたチャンクも、削除されたリビジョンを覚えておく（`/api/chunks` で「削除」として送るため）。
- **範囲の絞り込み**：`/api/chunks` は任意の `focus=x1,y1,z1,x2,y2,z2&margin=32` を受け取り、その範囲を `margin` ブロック広げた範囲に重なるチャンクだけを返す（サーバー側で絞る）。読み込まなかったチャンクとの境界は空気として扱い、切り口の面を描く。
- **チャンクのバイナリ**：`[チャンク数 u32][各チャンク: cx i32, cy i32, cz i32, 状態 u8 (0=存在, 1=削除), 4096 個の u16（存在のときのみ）]`、リトルエンディアン、gzip で圧縮する。値は「表示用パレット」の番号で、これは接続を解決したあとのブロック状態の番号である。接続の解決は隣のブロックに依存するので、あるチャンクが変わったら、隣り合う 6 チャンクも変わったものとして送り直す。
- **表示用パレットの番号**は、プロジェクトのパレットとは別に、プレビューサーバーがプロジェクトごとに追記のみで管理する。そのため、`/api/palette` は前回から増えた分だけを返せるように `since` を受け取る（実装の詳細は任せる）。
- 3D ビューアは、2 秒おきに `/api/status` を見て、`revision` が増えていれば変わったチャンクを取りに行く。
- `127.0.0.1` だけで待ち受けるのは、既存どおり。

### 4. ビューア（`src/preview/client/`、ブラウザ側）

- **言語とビルド**：TypeScript で書き、`tsc` で `dist/preview/client/*.js`（ES モジュール）に出力する。ブラウザは、サーバーが配信するそのファイルを直接読み込む（バンドラーは使わない）。`three` は `dependencies` に追加する。サーバーは `node_modules/three/build/` を `/vendor/three/build/`、`node_modules/three/examples/jsm/` を `/vendor/three/examples/jsm/` として配信する（r171 以降は `three.module.js` が `three.core.js` を読むため、ディレクトリごと配信する）。import map は `three` と `three/addons/` の両方を向ける。
- **Worker のコード**：module worker の中では import map が効かないことがあるので、Worker から読み込むコード（`mesher.ts` とその依存）は `three` を import せず、相対パスの import だけを使う。
- **メッシュ生成**（`mesher.ts`）：純粋な関数として作り、vitest でテストする。入力はチャンク 1 つ分と、隣の 6 チャンクの境界の値、表示用パレットの焼き込み済みモデル。出力は、透明度の分類ごとの頂点バッファ（位置、UV、色）である。
  - クアッドに `cullface` があり、その方向の隣のブロックがその面を完全に覆う不透明なブロックであれば、そのクアッドを描かない。
  - 同じ種類の半透明ブロック同士（ガラスとガラス、水と水）の間の面も描かない。
  - 陰影：上 1.0、下 0.5、北と南 0.8、東と西 0.6（Minecraft の固定陰影と同じ）。`shade: false` のクアッドには陰影を付けない。
  - 着色：草 `#91BD59`、葉 `#77AB2F`、水 `#3F76E4`。それ以外の `tintindex` は白とする（実装者が本家の色を足すのは自由）。
  - 断面スライダーで消した高さより上のブロックは描かない。消した高さのすぐ上の面は、隣が消えたものとして扱って描く（断面が中まで見えるようにするため）。断面を変えたときは、影響する高さのチャンクだけメッシュを作り直す。
- **メッシュの作成場所**：Web Worker で作る。メインスレッドを固めないためである。
- **テクスチャ**：ブロックのテクスチャ（16×16 が基本。縦長のアニメーション用の画像は、最初の 16×16 を使う）を、1 枚のアトラス画像にまとめる。描画は最近傍補間（ピクセルがぼやけないように）にする。アトラスは、パレットに出てくるテクスチャだけで作る。新しいテクスチャが出てきたら作り直す。
- **描画の順序**：不透明、カットアウト、半透明の順に描く。半透明はチャンク単位で、カメラから遠い順に並べる。
- **カメラ**：
  - `OrbitControls` で回転、パン、ズームする。
  - プリセット：`top`（真上）、`iso_ne`、`iso_nw`、`iso_se`、`iso_sw`（斜め上 45 度。たとえば `iso_ne` は北東から見下ろす）、`north`、`south`、`east`、`west`（その方角から水平に見る。`north` は北側から南を向いて見る）。プリセットは、表示範囲全体（または `renderView` で指定した範囲）が画面に収まる距離にカメラを置く。
  - 投影は透視投影を既定にする。`top` だけは、平行投影に切り替えるボタンを付ける（配置の確認や、第 4 段階のマーカーとの照合で、平面図として見たいため）。
- **UI**：プロジェクト名、リビジョン、アセットの状態、解決できなかった ID の一覧、視点プリセットのボタン、断面スライダー（Y の最小値〜最大値）、ホバーで出る座標と ID、クリックで座標をコピー、2D ビューアへのリンク。
- **選択の判定**：ホバーとクリックは、レイキャストでブロックを特定する。メッシュとの交差ではなく、ボクセルの格子をたどる方式でよい（DDA）。
- **完了の合図**：最初の全チャンクの読み込み、メッシュの作成、テクスチャの読み込みがすべて終わって、1 フレーム描画したら、`window.__previewReady = true` にする。URL のパラメータに `view`、`clipY`、`focus`（範囲 `x1,y1,z1,x2,y2,z2`）、`ui=0`（UI を隠す）、`ortho=1` を受け付け、その状態で開けるようにする（`renderView` が使う）。

### 5. `renderView` ツール（`src/preview/render-view.ts`、`src/tools/`）

- **入力**：
  - `view`：上のプリセット名。既定は `iso_se`。
  - `focus`：任意の範囲 `{ from, to }`。省略時は、プロジェクト全体のバウンディングボックス。
  - `clipY`：任意。この高さより上を描かない。
  - `width`、`height`：既定 1280×800、最大 1920×1200。
  - `ortho`：任意。`top` のときだけ効く。
  - `project`：任意。省略時はアクティブなプロジェクト。
- **処理**：
  1. プレビューサーバーを起動する（起動していなければ）。
  2. `playwright-core` で、PC に入っている Edge（`channel: 'msedge'`）を、なければ Chrome（`channel: 'chrome'`）をヘッドレスで起動する。
  3. パラメータ付きの URL を開き、`window.__previewReady` を最大 120 秒待つ（テクスチャの取得を含む）。
  4. スクリーンショットを撮る。
- **ブラウザ**：撮影のたびに起動すると遅いので、プロセスの中で 1 つだけ使い回す。プレビューサーバーも、`previewBuild` と共用の 1 つ（`127.0.0.1` の OS が割り当てるポート）を使う。最後の使用から 5 分経ったら閉じる。MCP サーバーの終了時にも閉じる。
- **出力**：MCP の `image` コンテンツ（`image/png`、base64）と、`text` コンテンツ（視点、範囲、断面、アセットの状態、解決できなかった ID の一覧）。
- **ブラウザが見つからないとき**：Edge も Chrome も見つからなければ、そのことと「Edge か Chrome をインストールしてください」をエラーで返す。
- **依存ライブラリ**：`playwright-core` を追加する（ブラウザ本体はダウンロードしない）。
- **WebGL**：ヘッドレスの Edge と Chrome は、GPU がなくてもソフトウェアの WebGL（SwiftShader）で描画できる。ただし、新しいバージョンでは自動の切り替えが廃止されつつあるので、起動引数に `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader` を明示する。WebGL のコンテキストが作れなかったら、ビューアは `window.__previewError` に理由を入れ、`renderView` はそれをエラーとして返す。
- **大きなマップ**：`renderView` は 1 フレームを撮るだけなので、描画そのものより、読み込みとメッシュ生成の時間が効く。そこで次のようにする。
  - `focus` を指定したときは、`focus` から 32 ブロック以上外のチャンクを読み込まない（§3 の範囲の絞り込み）。
  - メッシュは、`navigator.hardwareConcurrency`（最大 8）個の Worker で並列に作る。
  - 目標：500×80×500 の街の全体を `iso_*` で撮るのが 60 秒以内（テクスチャのキャッシュがある状態）。これを `pnpm test:e2e` で確かめる。届かない場合は、遠くのチャンクは各列の一番上の面だけを描く簡易表示（LOD）を、実装者の判断で追加してよい。追加したら、本書に追記すること。

### 6. ツールの説明文

### 8. テスト

- モデルの解決（Node、vitest）：テスト用の小さな blockstates とモデルの JSON を `test/fixtures/` に置いて使う（本物の jar には依存しない）。`variants` の一致、`multipart` の `OR` と `|`、`parent` の継承とテクスチャ変数、要素の回転、バリアントの `x`/`y` の回転、解決できない ID。
- メッシュ生成（Node、vitest）：完全なブロック 2 つが隣り合うと、間の面が 2 枚とも消えること。ガラス同士の間の面が消えること。ハーフブロックの上面は、上に石があっても消えないこと（下側の `cullface` だけが効く）。断面スライダーで切った高さで、面が描かれること。
- アセットの取得：manifest、メタデータ、jar の取得部分をモックにして、sha1 の不一致でエラーになること、`.complete` がなければ取得し直すこと。
- サーバー：`/api/chunks` の `since` で、変わったチャンクとその隣だけが返ること。チャンクのバイナリ形式。
- 視点プリセット：各プリセットのカメラの位置と向きを数値で固定するテスト（`north` で画面の左が +X になること、`top` で画面の上が −Z になること）。カメラの計算は純粋な関数に切り出して、Node でテストする。
- 色の使い分け：テクスチャの取得に失敗したときは `block-colors.ts` の `colorFor`（未知の ID にもハッシュで色を返す）で塗る。モデルを解決できない ID は、テクスチャの有無に関係なくマゼンタと黒の市松模様にする。
- `renderView`：ブラウザを起動する部分をモックにして、URL のパラメータと、画像と文字の 2 つのコンテンツが返ることを確認する。実際の Edge を使う結合テストは、`test/perf` と同じように通常のテストから外し、`pnpm test:e2e` で手動で実行する。結合テストは、小さなプロジェクトを `renderView` で撮影して、PNG が返り、真っ黒でも真っ白でもないことを確認する。
- 手動確認：本物の jar を取得し、階段、ハーフブロック、フェンス、ガラス板、扉、葉、水、色付きガラスを並べたプロジェクトを、ブラウザと `renderView` の両方で目視で確認する。

## 実装者に任せること

- アトラスの詰め方、Worker とのやり取りの形式。
- `uvlock` の近似の精度。
- 透明度の分類表の中身（主なブロックは必ず含めること）。
- 3D ビューアの見た目の細部（色、配置）。2D ビューアの雰囲気に揃える。
- `/api/palette` の差分の返し方。

## 実装の割り振り（ユーザーの方針）

モデルの解決（§2）とメッシュ生成（§4 の `mesher.ts`）は難所なので、Opus（メインセッション、または Opus のサブエージェント）が担当する。それ以外（アセットの取得、サーバーの API、UI、`renderView`、ドキュメント）は、Sonnet のサブエージェント 1 体が通しで担当する。
