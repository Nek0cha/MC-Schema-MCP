# 設計書: ビルドプレビュー機能（ローカルHTTPビューア）

- 日付: 2026-09-01
- ステータス: レビュー待ち

## 背景・目的

現状、AIはビルド中のプロジェクトを一切「見る」手段がなく、`getBuildInfo` が返すサイズ・バウンディングボックス・ブロック数集計だけを頼りに配置している。これにより、意図しない位置へのブロック配置や、シルエット・視認可能面の判断ミスが起きやすい。

本機能は、アクティブ（または指定）プロジェクトの状態をブラウザで視覚的に確認できるローカルWebビューアを追加する。ユーザーが目視で確認できることに加え、座標をクリックでコピーできるようにし、「このブロックの座標を知りたい」というユースケースを解消する。

## スコープ

**やること**
- Y軸スライス（水平断面、X-Z平面）を1枚ずつ表示する2Dビューア
- ブロックIDに応じた色分け（本物のMinecraftテクスチャは使わない）
- レイヤー切り替え、ズーム、パン
- セルのホバーで座標+ブロックID表示、クリックで座標をクリップボードにコピー
- 新規MCPツール `previewBuild` から、ローカルHTTPサーバーのURLを返す

**やらないこと（YAGNI / 将来拡張の余地として明示的に見送る）**
- 3Dレンダリング（Three.js等）— 陰影表現が要る割に本機能の目的（座標確認・大まかな配置確認）に対してオーバースペック
- 本物のMinecraftテクスチャの利用（jarからの抽出含む）— 実装コストが大きく、著作権面の配慮も必要になるため今回は見送り
- X軸・Z軸方向のスライス（立面図）— 初期実装はY軸スライスのみ。必要になれば同じAPIを拡張して対応できる設計にしておく
- ページの自動ライブ更新（WebSocket等）— ユーザーが手動でブラウザをリロードする前提
- 複数プロジェクトの同時表示

## アーキテクチャ

```
previewBuild ツール呼び出し
  → ローカルHTTPサーバーが未起動なら起動（127.0.0.1、遅延起動、以後プロセス生存中は使い回す）
  → "http://127.0.0.1:<port>/?project=<name>" をテキストで返す
  → ユーザーがブラウザでURLを開く
  → ページが GET /api/build?project=<name> を叩いて voxel データを取得し、canvas に描画
```

### 新規ファイル

- **`src/preview/server.ts`** — Node標準の `http` モジュールのみで実装するローカルサーバー。外部依存を増やさない。`127.0.0.1` にのみバインドし、外部からのアクセスを防ぐ。
  - `GET /` — ビューアのHTML（インラインCSS/JS、外部CDN依存なし）
  - `GET /api/build?project=<name>` — 指定プロジェクト（省略時はアクティブプロジェクト）の voxel データをJSONで返す
  - サーバーインスタンスはモジュールスコープの変数で保持し、2回目以降の `previewBuild` 呼び出しでは起動をスキップして同じポートを返す
- **`src/preview/block-colors.ts`** — `colorFor(blockId: string): string` を公開。stone/dirt/wood/wool系など代表的な素材は手動テーブルで自然な色を割り当て、テーブルにないIDはID文字列からハッシュ値を計算し決定的なHSL色に変換する（同じIDは常に同じ色になる）。`minecraft:air` は専用の薄いグレーを返す。
- **`src/tools/preview-tools.ts`** — `previewBuildHandler(manager, portState)`。サーバーを起動（または既存のものを再利用）し、URLをテキストで返す。

### 既存ファイルへの変更

- **`src/server.ts`** — `previewBuild` ツールを登録（引数なし、または任意で `project?: string`）
- **`README.md`** — ツール一覧に `previewBuild` を追記

## データAPI仕様

`GET /api/build?project=<name>`（`project` 省略時はアクティブプロジェクト）

```json
{
  "project": "castle",
  "bounds": { "min": { "x": 0, "y": 60, "z": 0 }, "max": { "x": 20, "y": 80, "z": 20 } },
  "blocks": [
    { "x": 0, "y": 64, "z": 0, "id": "minecraft:stone" }
  ]
}
```

- `blocks` はプロジェクトの `voxels` をそのままフラット配列化したもの（airは配列に含まれず、クライアント側で「データがない座標=air」として扱う）
- プロジェクトが存在しない、またはアクティブプロジェクトが無い場合は `404` とエラーメッセージのJSON
- ブロック数が将来的に問題になるレベルまで巨大化した場合は `&y=<layer>` によるレイヤー単位取得に拡張できるようにエンドポイント設計をしておく（今回は実装しない）

## UI仕様

- ページ上部: プロジェクト名表示、レイヤー切り替え（`Y: 64` 表示 + `◀`/`▶` ボタン + 直接入力）。初期表示レイヤーは `bounds.min.y`
- メインエリア: 現在のYレイヤーのX-Z平面をcanvasに描画。1ブロック=1セルの正方形、色は `block-colors.ts` 相当のロジックをクライアントJS側に埋め込んで計算（サーバーAPIはIDのみ返し、色決定はクライアント側で行う。サーバー実装と重複するが、静的HTML1枚に完結させるための単純化）
- ホバー: ツールチップで `(x, y, z) minecraft:block_id`
- クリック: `x,y,z` 形式の文字列を `navigator.clipboard.writeText()` でコピーし、セルを一瞬ハイライトして視覚フィードバック
- ズーム: マウスホイールで拡大縮小。パン: ドラッグ
- レスポンシブは考慮しない（ローカルのデスクトップブラウザ利用が前提）

## エラーハンドリング

- アクティブプロジェクトが無い状態で `previewBuild` を呼んだ場合: ツールはエラーではなく「サーバーは起動するが、開くとプロジェクトが無い旨を表示するページになる」ではなく、**ツール呼び出し時点でエラーを返す**（`ProjectManager.getActive()` が投げる例外をそのまま伝播させる。既存の他ツールと同じ挙動に揃える）
- プロジェクトに1つもブロックが無い場合: `/api/build` は `bounds: null, blocks: []` を返し、ページは「ブロックがありません」と表示する

## テスト方針

- `src/preview/block-colors.ts` の色決定ロジック: 手動マッピングされたIDが正しい色を返すこと、未知のIDが決定的な色を返すこと（同じ入力→同じ出力）、airが専用色を返すことをユニットテスト
- `src/preview/server.ts` の `/api/build` エンドポイント: 実際にHTTPリクエストを投げて、プロジェクトの内容が正しくJSON化されて返ることを検証（`node:http` でリクエストするか、`fetch` を使う）
- `previewBuildHandler`: サーバーが起動しURLを返すこと、2回目の呼び出しで同じポートが再利用されること
- ビューアHTML/JS自体（canvas描画・クリック・クリップボード）は自動テスト対象外とし、手動確認とする
