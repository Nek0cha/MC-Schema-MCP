# 設計書: レイドマップの書き出し（.nbt タイル、map.json、マーカー、自動検証）

- 日付: 2026-11-08
- ステータス: ユーザー確認待ち
- 位置づけ: 改善ロードマップ 4 段階のうち第 4 段階（最後）。第 1〜3 段階（チャンク型の保存と永続化、編集ツールとテンプレート、3D プレビューと `renderView`）を前提にする。

## 背景・目的

NeoForge **1.21.1** 用の抽出シューター MOD で使うレイドマップを、MC-Schema-MCP で作って書き出したい。MOD はレイドのたびに専用のディメンションへマップを貼って、状態をリセットする。マップの例は廃墟の街や軍の基地で、1 回のレイドは 10〜20 分を想定している。

MOD 側の要件（ユーザーから受け取ったもの）は次のとおり。

- **規模**：300〜500 ブロック四方。高さは地下 16、地上 64 程度。バニラのブロックだけを使う。
- **ファイル**：バニラの構造ファイル（`.nbt`、StructureTemplate 形式）を、48×48（高さは全体）のタイルに分けて、`tile_<x>_<z>.nbt` として書き出す。マップごとに 1 フォルダにまとめ、`map.json` と、真上から見た `preview.png` を付ける。
- **map.json**：プレイヤーのスポーン、脱出地点、箱、敵のスポーン、巡回ルートを、マップの北西の一番下の角を原点にした相対座標で書く。
- **地形のルール**：敵の通路は幅 2 以上。段差は 1 ブロックまで。遮蔽物を置く。外周を囲う。屋内に光源を置く。
- **検証**：書き出しのたびに、次の 7 項目を自動で確かめる。
  1. 座標がすべて範囲内にある。
  2. 各地点の足元が固体で、上に 2 ブロックの空間がある。
  3. 各スポーンから、すべての脱出地点へ歩いて行ける。
  4. 巡回ルートの隣り合う地点の間を歩いて行ける。
  5. 箱の位置が、空気か樽になっている。
  6. タイルの数と `size` が合っている。
  7. 各地点を色分けして重ねた `preview.png` を出す。

## ユーザーが決めたこと

- 検証で問題が見つかっても、ファイルは書き出す。結果は報告するだけにする。
- タイルには空気も書き込む（既定）。MOD は「たぶん」ディメンションを作り直しているが、確かではない。上書きで貼り直す方式でもリセットが効くよう、空気を書くのを標準にする。設定でオフにできる。

## ゴール

- アクティブなプロジェクトを「マップ」として設定し（`map_id`、名前、大きさ、対象バージョン）、マーカーを置き、1 回のツール呼び出しで、要件どおりのフォルダ一式を書き出せる。
- `.nbt` は、Minecraft 1.21.1 の `StructureTemplate` として読み込める形式である（`DataVersion = 3955`）。
- 1.21.1 に存在しないブロック ID とプロパティを使っていたら、警告を出す。
- 検証の 7 項目に加えて、要件の数の条件（スポーンが 6 か所以上で、互いに 60 ブロック以上離れている、など）も確認し、結果を一覧で返す。
- マーカーは、3D プレビューと `renderView` に色分けして表示される。AI が配置を目で確かめられる。
- テンプレートに箱と敵のスポーンのマーカーを含められる。建物を並べると、中の箱の位置も一緒に配置される。

## 非ゴール

- MOD 側の実装（箱の中身、敵の AI、レイドの進行）。
- 屋内の明るさの検証（光源の自動チェック）。スキルの心得として扱う。
- 遮蔽物の間隔、乗り越え用の障害物、高さ 1 の窓の自動チェック。スキルの心得として扱う。
- ブロックエンティティの中身（チェストの中身、看板の文字など）を `.nbt` に書くこと。
- 1.21.1 と 1.21.11 以外のバージョン。

## アンチゴール

- 書き出した `.nbt` を 1.21.1 で読み込むと、ブロックが化ける、または読み込めない。
- 検証が「歩いて行ける」と言ったのに、実際の地形では行けない（あるいはその逆）ことが頻繁に起きる。完全な一致は求めないが、要件のルール（段差 1 ブロックまで、幅 1 以上）について、誤判定が出る典型的なパターン（階段、ハーフブロック、扉、フェンス）は正しく扱う。
- 検証の結果が長すぎて、AI が要点をつかめない。
- 検証に時間がかかりすぎる（500×80×500 で、目安 30 秒以内）。

## 設計

### 1. マップの設定（プロジェクトのメタデータ）

- アクティブなプロジェクトに、マップの設定を持たせる。`project.json` に任意のフィールド `map` を追加する（`formatVersion` は 1 のまま。古い読み込み処理は未知のフィールドを無視するため）。

```json
"map": {
  "id": "ruined_town",
  "name": "廃墟の街",
  "size": [400, 80, 400],
  "targetVersion": "1.21.1",
  "includeAir": true
}
```

- **座標系**：プロジェクトの座標をそのままマップの座標とする。マップの範囲は `(0,0,0)` 〜 `(size.x-1, size.y-1, size.z-1)` である。地下 16 を含める場合、地上の地面はおおよそ y=16 になる（スキルに書く）。
- `map.id` はプロジェクト名と同じ規則で検証する。`targetVersion` は `'1.21.1' | '1.21.11'`（既定 `'1.21.1'`）。`includeAir` の既定は `true`。

### 2. マーカー

- プロジェクトのディレクトリに `markers.json` として保存する。変更のたびに、アトミックに書き直す（第 1 段階の `writeAtomic`）。
- 種類と内容は、`map.json` の要件に合わせる。各マーカーには、内部 ID（`m1`、`m2` … の連番）を付ける。

| kind | フィールド |
|---|---|
| `player_spawn` | `pos`、`facing`（Minecraft の yaw：0=南、90=西、180=北、270=東） |
| `extract` | `id`（文字列、マップ内で一意）、`pos`、`radius`（既定 4） |
| `loot` | `pos`、`type`（`crate` / `safe` / `weapon_case` / `medical`）、`tier`（1〜3） |
| `enemy_spawn` | `pos`、`squadSize`（`[min, max]`）、`tier`（1〜3） |
| `patrol_route` | `id`（文字列、一意）、`points`（2 点以上） |

- `pos` は、**足のあるマス**（その上に立つブロックの 1 つ上）を表す。`loot` の `pos` は、箱を置くマスである。
- **ツール**（すべて `withSave` で包む。`addMarkers` と `removeMarkers` は `batch` で使える）：
  - `setMapSettings { id, name, size, targetVersion?, includeAir? }`
  - `addMarkers { markers: Marker[] }`：`kind` で区別する union。一意性（`extract.id`、`patrol_route.id`）を確かめる。追加した内部 ID を返す。
  - `listMarkers { kind? }`：内部 ID 付きで、種類ごとにまとめて返す。
  - `removeMarkers { ids }`
- **テンプレートとの連携**：`saveTemplate` は、範囲内の `loot` と `enemy_spawn` のマーカーを、基準点からの相対座標でテンプレートに含める（テンプレートのファイルに任意のフィールド `markers` を追加する）。`placeTemplate` は、それらを回転・反転した位置に追加する。テンプレートを置くたびに、箱の位置も一緒に増える。
- **一括移動との関係**：`copyRegion` や `stackRegion` は、マーカーをコピーしない（意図しない重複を避けるため）。スキルにその旨を書く。

### 3. タイルの書き出し（`src/schematic/structure-writer.ts`）

- `StructureTemplate` の NBT（gzip 圧縮）：

```
{
  DataVersion: Int,             // 1.21.1 → 3955、1.21.11 → 4671
  size: List<Int>[sx, sy, sz],
  palette: List<{ Name: String, Properties?: Compound<String> }>,
  blocks: List<{ pos: List<Int>[x, y, z], state: Int }>,
  entities: List (空)
}
```

- タイル `(tx, tz)` は、x が `tx*48` 〜 `min(size.x, (tx+1)*48) - 1`、z も同様の範囲で、y は 0 〜 `size.y - 1` の全体を含む。端のタイルは 48 より小さくなる（埋めない）。タイルの数は `ceil(size.x/48) × ceil(size.z/48)`。
- ブロックの状態は、第 2 段階の接続の解決を適用したものを書く。
- `includeAir: true` のとき、未設定のマスと明示的な空気は、すべて `minecraft:air` として書く。`false` のとき、どちらも書かない（`blocks` に含めない）。
- マップの範囲外にあるブロックは書かない。検証で警告する。
- 実装は既存の `@enginehub/nbt-ts` を使う。`writer.test.ts` と同じ方針で、読み戻すテストを書く（NBT を decode して構造を確かめる）。

### 4. 1.21.1 との互換性チェック

- 第 3 段階の `AssetStore` を、`targetVersion` のバージョンで別に持つ（キャッシュは `cache/assets/1.21.1/`）。その `blockstates/*.json` のファイル名の一覧を、存在するブロック ID の一覧とする。
- プロパティ名の一覧は、`variants` のキーと `multipart` の `when` のキーから集める。値の一覧は集めない（名前の確認だけ）。
- プロジェクトで使っている各ブロック状態について、ID がなければ警告、ID はあるが知らないプロパティ名があれば警告。警告は ID ごとにまとめて、個数を添える。
- アセットを取得できなかったときは、「互換性を確かめられなかった」という警告を 1 つ出して先へ進む。

### 5. 検証（`src/raid/validate.ts`、`src/raid/walk-grid.ts`）

#### 歩く人の想定

- 検証 3（スポーン → 脱出地点）は `player_spawn` だけを起点にする。検証 4 は巡回ルート（敵）を対象にする。どちらも、**要件に書かれた規則**（段差は 1 ブロックまで、上りも下りも）で判定する。本家のモブは 3 ブロックまで飛び降りられるが、要件の規則のほうが厳しいので、要件に合わせる（屋上から飛び降りないと行けない道は「行けない」と判定される。これは意図どおりで、スキルにも書く）。
- 幅 2 の確認は、巡回ルートにだけ行う（警告）。

#### 歩行グリッド

マップの範囲内の各マスについて、「そのマスに足を置いて立てるか」と「立ったときの足の高さ」を前計算する。

- **衝突の高さ** `top(block)`：そのブロックの上面の高さ。
  - 0（衝突なし）：空気、未設定、草花、松明、ボタン、レバー、看板、旗、レール、レッドストーン、水（泳ぎは扱わない。水の中は通れるが、足場にはならない）、開いたフェンスゲート、木の扉（敵は開けられる。要件で使ってよいとされている）、はしご（下記の上下移動の規則を使う）。
  - 1/16：カーペット。3/16：閉じた下付きのトラップドア。
  - 0.5：下付きのハーフブロック。
  - 1：通常のブロック、上付きのハーフブロック、ダブルのハーフブロック、階段、閉じた上付きのトラップドア。高さが 0.5 より大きく 1 より小さいもの（ベッド、チェスト、土の道、耕地、ソウルサンドなど）も 1 として扱う。**表にないブロックの既定値も 1**（固体）とする。
  - 通れない（上に立てず、通り抜けもできない）：フェンス、壁、閉じたフェンスゲート（本家のモブも上を歩かない）、鉄の扉、溶岩、サボテン、マグマブロック、火、粉雪、蜘蛛の巣、スイートベリーの茂み（モブが避けるもの）。
  - 分類は ID のパターンの表で行う（実装者が拡張してよい）。
- **立てるマス** `(x, y, z)`：
  - 足のマスの衝突の高さが 0.5 以下で、頭のマス `(x, y+1, z)` の衝突の高さが 0 である。どちらも「通れない」ブロックではない。
  - 足のマスの高さが 0 より大きい（カーペット、下付きのハーフブロックなど）とき、`L = y + top(足のマス)` とする。ただし、その下のマスが空気なら立てない（浮いたカーペットに立つのを防ぐ）。
  - 足のマスの高さが 0 のときは、下のマスを見て `L = y - 1 + top(下のマス)` とし、`top(下のマス)` が 1 であること（固体の上に立つ）。
- **移動**：東西南北の隣の立てるマスへ、`|ΔL| ≤ 1` のとき移動できる。はしごがあるマスとその真上・真下のはしごのマスの間は、上下にも移動できる。斜めの移動はしない（斜めにしかつながっていない細い道は「行けない」と判定されるが、要件の通路の幅を満たす地形では起きない）。
- **幅 2 の判定**（敵用）：あるマスを含む 2×2 の正方形の 4 マスが、すべて立てるマスで、`L` の差が 0.5 以下のとき、そのマスは「幅 2」である。

#### 検証の項目

| # | 内容 | 重さ |
|---|---|---|
| 1 | すべてのマーカーの座標が範囲内。範囲外のブロックがないか | エラー（ブロックは警告） |
| 2 | `player_spawn`、`extract`、`enemy_spawn`、`patrol_route` の各点が「立てるマス」 | エラー |
| 3 | 各スポーンから各脱出地点へ、歩行グリッドの上で到達できる（脱出地点の `pos` から `radius` 以内の立てるマスに着けば到達とする） | エラー |
| 4 | 巡回ルートの隣り合う 2 点の間を到達できる。加えて、幅 2 のマスだけでも到達できるか | 前者はエラー、後者は警告 |
| 5 | `loot` の `pos` が、空気、未設定、樽のどれか | エラー |
| 6 | 書き出したタイルの数とファイル名が、`size` から計算した数と一致する | エラー |
| 7 | `preview.png` を書き出した | エラー（書けなかった場合） |
| 8 | スポーンが 6 か所以上、互いに水平距離で 60 以上離れている | 警告 |
| 9 | 脱出地点が 4 か所以上 | 警告 |
| 10 | tier 3 の箱から 32 ブロック以内に tier 3 の敵のスポーンがある | 警告 |
| 11 | 外周：スポーンから歩いて、マップの外周（x=0、x=size.x−1、z=0、z=size.z−1）の立てるマスに着ける場合、外周を越えられる可能性がある | 警告 |
| 12 | 1.21.1 との互換性（§4） | 警告 |
| 13 | 孤立したガラス板（第 2 段階） | 警告 |

- **到達できなかったとき**は、到達できた範囲の中で目標に最も近いマスの座標と、その距離を書く。AI がどこで道が途切れているかを探しやすくするためである。
- **性能**：歩行グリッドは `Uint8Array` などの型付き配列で持つ。到達の判定は、スポーンごとに 1 回の幅優先探索で、すべての脱出地点をまとめて調べる。目標は 500×80×500 で 30 秒以内。
- **結果の形**：

```ts
interface ValidationReport {
  ok: boolean;             // エラーが 0 件
  errors: Issue[];
  warnings: Issue[];
  stats: { tiles: number; blocks: number; markers: Record<string, number>; durationMs: number };
}
interface Issue { check: number; message: string; at?: [number, number, number] }
```

- ツールのレスポンスは、最初に `OK` か `N errors, M warnings` を書き、続けてエラーを最大 20 件、警告を最大 20 件書く（超えた分は件数だけ）。全文は `validation.json` に書く。

### 6. preview.png（`src/raid/preview-png.ts`）

- 真上から見た平面図。1 ブロックを 2×2 ピクセルで描く（400 四方なら 800×800）。
- 各列の一番上のブロックの色で塗る。色は、アセットがあればテクスチャの平均色、なければ `colorFor`。高さに応じて明るさを変える（低いほど暗く）。
- マーカーを重ねる：
  - プレイヤーのスポーン：緑の丸と、向きを示す短い線
  - 脱出地点：水色の丸と、`radius` の円
  - 箱：黄色の四角（tier が高いほど濃い）
  - 敵のスポーン：赤の丸
  - 巡回ルート：橙色の線（点の順に結ぶ）
- 右下に凡例を描かない（文字の描画に依存ライブラリが要るため）。凡例は `map.json` の隣の `preview-legend.txt` に書く。
- PNG のエンコードは、Node の `zlib` で自前で書く（依存ライブラリを増やさない）。

### 7. 書き出しのツール

- `validateRaidMap {}`：ファイルは書かずに、検証だけを行う（7 の preview の項目は省く）。
- `exportRaidMap { outputDir? }`：既定は `./output/maps/<map.id>/`。次を書いてから、検証を行う。

```
<map_id>/
  map.json
  tiles/tile_<x>_<z>.nbt
  preview.png
  preview-legend.txt
  validation.json
```

- 書き出し先に古いタイルがあれば、消してから書く（タイル数が減ったときに古いファイルが残らないようにするため）。消すのは `tiles/` の `tile_*.nbt` だけにする。
- `map.json` は、要件の例（下）と同じ形で書く。キーはこの例のとおり、座標はすべて `[x, y, z]` の配列、`facing` は yaw の数値、`type` と `tier` はマーカーの値をそのまま書く。キーの順序もこの例に合わせる。マーカーの内部 ID と、`targetVersion`、`includeAir` は書かない。

```json
{
  "id": "ruined_town",
  "name": "廃墟の街",
  "size": [400, 80, 400],
  "tile_size": 48,
  "player_spawns": [ { "pos": [12, 20, 30], "facing": 90 } ],
  "extracts": [ { "id": "north_gate", "pos": [200, 20, 5], "radius": 4 } ],
  "loot": [ { "pos": [150, 22, 160], "type": "crate", "tier": 2 } ],
  "enemy_spawns": [ { "pos": [180, 20, 170], "squad_size": [2, 4], "tier": 2 } ],
  "patrol_routes": [ { "id": "route_a", "points": [[180,20,170], [220,20,170], [220,20,220]] } ]
}
```

- タイルのファイル名の `<x>` と `<z>` は、0 から始まる**タイルの番号**（ブロック座標ではない）。要件の原文どおりである。タイル `(tx, tz)` を置く位置は、マップの原点から `(tx*48, 0, tz*48)` である。
- `size.x` か `size.z` が 48 の倍数でないと、端のタイルが 48 より小さくなる。それ自体は許すが、MOD がタイルの大きさを固定で扱っている可能性に備えて、検証で警告する（「48 の倍数（384、432、480 など）にすると、端のタイルも 48×48 になる」）。
- 書き出しはタイルごとに行い、マップ全体の NBT をメモリに一度に作らない。
- マップの設定がないプロジェクトで呼んだら、`setMapSettings` を先に呼ぶよう案内するエラーにする。

### 8. 3D プレビューへのマーカー表示

- `GET /api/markers?project=` を追加し、ビューアはステータスと一緒にポーリングする。
- 表示は §6 と同じ色。地点は、足のマスに立つ高さ 2 の半透明の柱。脱出地点は、地面に `radius` の輪。巡回ルートは、点を結ぶ線。箱は、マスに収まる黄色の箱の枠。
- 「マーカーを表示」のチェックボックスを付ける（既定でオン）。`renderView` の URL パラメータ `markers=0` で消せる。
- ホバーしたとき、マーカーの種類と内容を表示する。

### 9. スキル

`building-minecraft-schematics` に「レイドマップ」の節を追加する。

- 作り方の順序：`createProject` → `setMapSettings` → 地形（地下 16 段 + 地面）→ 外周の壁 → 道路 → テンプレートで建物 → `decayRegion` → マーカー → `renderView` で確認 → `validateRaidMap` → 直す → `exportRaidMap`。
- 要件の地形ルール（遮蔽物の高さ 1 と 2 の両方、20 ブロックおきの遮蔽物、乗り越え用の高さ 1・奥行き 1 の障害物、高さ 1 の窓、扉は木の扉か開口部、トラップドアで道をふさがない、通路は幅 2 以上、屋内に光源）。
- 箱の位置は空気にしておく（MOD が置く）。樽を置いてもよい。
- 1.21.1 に存在しないブロック（銅の格子、新しい木の種類など）を使わない。警告が出たら置き換える。

### 11. テスト

- 歩行グリッド：平地、1 段の段差（行ける）、2 段の段差（行けない）、階段で 2 段上る（行ける）、ハーフブロックの段差、フェンス（越えられない）、木の扉（通れる）、鉄の扉（通れない）、はしごで上る、天井が低い（頭がつかえる）、幅 1 と幅 2 の通路。
- 検証の各項目：それぞれ、合格する小さなマップと、不合格になる小さなマップで確かめる。到達できないときに、最も近いマスが報告されること。
- `.nbt`：書き出したタイルを decode して、`DataVersion`、`size`、パレット、ブロックの位置と状態、空気の有無（`includeAir`）、端のタイルの大きさ、接続の解決を確かめる。
- `map.json`：要件の例と同じ形になること。
- `preview.png`：PNG として正しく読めること（自前のデコードか、ヘッダーと CRC の確認）。マーカーの色のピクセルが、期待した位置にあること。
- マーカー：追加、一覧、削除、一意性、保存と再読み込み、テンプレートでの回転。
- 性能：500×80×500 の疑似的な街で、`exportRaidMap` の全体が 60 秒以内、検証が 30 秒以内（`pnpm test:perf` に追加）。
- 互換性：テスト用の `AssetStore` のフィクスチャで、存在しない ID と、知らないプロパティ名が警告されること。

## 実装の割り振り（ユーザーの方針）

歩行グリッドと検証（§5）は難所なので、Opus（メインセッション）が担当する。それ以外（マップの設定、マーカー、`.nbt`、互換性チェック、preview.png、書き出し、ビューア、ドキュメント）は、Sonnet のサブエージェント 1 体が通しで担当する。
