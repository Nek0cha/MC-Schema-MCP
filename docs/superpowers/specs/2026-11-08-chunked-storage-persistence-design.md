# 設計書: チャンク型ボクセル保存とプロジェクトの永続化

- 日付: 2026-11-08
- ステータス: ユーザー確認待ち
- 位置づけ: 改善ロードマップ 4 段階のうち第 1 段階

## 背景・目的

NeoForge 1.21.1 用の抽出シューター MOD のレイドマップ（300〜500 ブロック四方、地下 16〜地上 64 程度、最大でおよそ 500×80×500 = 2,000 万セル）を MC-Schema-MCP で作りたい。現状の実装には、この規模に対して次の 2 つの問題がある。

1. **メモリ効率**：`BuildProject.voxels` が `Map<"x,y,z", BlockState>` で、1 セルごとに文字列キーとオブジェクトを持つ。数百万セル規模になると、メモリ使用量が数百 MB から GB 単位まで膨らむ見込みである。
2. **揮発性**：プロジェクトはプロセスのメモリ上にしかない。MCP サーバーの終了や Claude Code の再起動で、作業内容がすべて失われる。大規模マップは複数セッションにまたがって作るため、これは致命的である。

本段階では、ボクセルの保存をチャンク単位の配列に置き換え、プロジェクトをディスクに自動保存して再開できるようにする。後続の段階はすべてこの上に乗る。

- 第 2 段階：編集ツール（コピーと貼り付け、置き換え、stack、rotate/flip、テンプレート、一括操作、孤立ブロックの警告）
- 第 3 段階：テクスチャ付き 3D プレビュー
- 第 4 段階：レイドマップの書き出し（`.nbt` タイル、`map.json`、自動検証）

## ゴール

- 500×80×500 を全セル埋めても、Node プロセスのメモリが現実的な範囲（目安として 500 MB 以下）に収まる。
- プロジェクトへの変更が、ツール呼び出しのたびにディスクへ自動保存される。プロセスを再起動しても、`listProjects` / `switchProject` で続きから作業できる。
- 既存の MCP ツールの入出力（引数とレスポンス文面）は変えない。既存テストはすべて通る。

## 非ゴール

- 編集ツール、テンプレート、一括操作（第 2 段階）
- プレビューの大規模対応（第 3 段階）。本段階では、プレビューサーバーを新しい API で動くように直すだけにする。巨大なプロジェクトを今の 2D ビューアで開くと重いが、それは許容する。
- `.schem` 書き出しの 1,600 万セル上限の撤廃（第 4 段階で `.nbt` タイル出力を作るときに扱う）
- undo / 履歴
- 複数プロセスから同じプロジェクトへの同時書き込み

## アンチゴール（技術的に動いても失敗とみなすもの）

- 自動保存が遅く、ツール呼び出しのたびに体感できる待ち（目安 1 秒超）が発生する。
- 保存途中でプロセスが落ちたとき、プロジェクトが読み込めなくなる（壊れる）。
- 既存ツールの挙動、特に後勝ちの書き込みや接続プロパティの自動計算が変わる。

## 設計

### 1. ボクセルストア

`BuildProject` の内部を次の構造に置き換える。

- **チャンク**：16×16×16 = 4,096 セルの `Uint16Array`。値はプロジェクト単位のパレットのインデックスである。**0 は「未設定（何も置いていない）」を表す。**
- **チャンクの管理**：`Map<string, Chunk>`。キーはチャンク座標（`floor(x/16)` など）で作る。負の座標も扱う（`Math.floor` を使い、チャンク内オフセットは `((x % 16) + 16) % 16`）。
- **チャンクごとの非 0 セル数**を持つ。0 になったチャンクは Map から削除する。
- **パレット**：`BlockState` の配列と、`blockStateKey(block)` から番号を引く `Map`。番号 1 から順に割り当てる。**追記のみで、番号は変えない**（永続化の整合性のため）。上限は 65,535 種類で、超えたら例外を投げる。
- **ブロック種類ごとの個数**をパレット番号ごとに数えておく。`getBlockCounts()` はこれを ID 単位に集計して返す。

#### 空気の扱い

`minecraft:air` は従来どおり、通常のブロックとして保存する（現状も `setBlock` で空気を置くと `voxels` に入る。互換性を保つ）。明示的に置いた空気は、第 4 段階の書き出しで「上書きして消す」意味を持たせられる。これとは別に、セルを未設定に戻す `removeBlock(pos)` を追加する（第 2 段階の編集ツールで使う。本段階では MCP ツールとしては公開しない）。

#### 公開 API

```ts
class BuildProject {
  readonly name: string;
  setBlock(pos: Vec3, block: BlockState): void;
  getBlock(pos: Vec3): BlockState | undefined;   // 未設定なら undefined
  removeBlock(pos: Vec3): void;
  forEachBlock(cb: (pos: Vec3, block: BlockState) => void): void;
  get blockCount(): number;
  getBoundingBox(): BoundingBox | null;
  getBlockCounts(): Record<string, number>;
}
```

- `voxels` フィールドは廃止する。現在 `voxels` を直接触っている箇所（`connections.ts`、`preview/server.ts`）は `forEachBlock` に置き換える。
- `getBlock` が返す `BlockState` はパレット内の共有オブジェクトである。呼び出し側が書き換えないことを前提とする（型は `Readonly` にしてよい）。
- `getBoundingBox()` は非空チャンクのみを走査して計算し、書き込みがあるまで結果をキャッシュする。
- `voxelKey` / `parseVoxelKey` は `connections.ts` と `writer.ts` が引き続き使うので残す。
- `forEachBlock` の走査順は規定しない（チャンク順でよい）。`connections.ts` の上書き結果は位置をキーにしているので、順序に依存しない。プレビューの API が返すブロック配列の順序も、従来の挿入順から変わってかまわない。
- パレットは追記のみなので、もう置かれていないブロックがパレットに残る（死んだエントリ）ことを許容する。`getBlockCounts()` は個数が 0 のエントリを返さない。

#### 性能

- `fillBox` などはセルごとに `setBlock` を呼ぶ。そのため、`setBlock` はチャンク検索のコストを抑える必要がある。たとえば直前に触ったチャンクをキャッシュする。手段は実装者に任せる。
- 目標値：400×80×400（1,280 万セル）を `fillBox` 1 回で埋めるのが 10 秒以内。そのときのヒープ増加が 200 MB 以下。これを性能テストで確認する（CI で不安定になりそうなら、閾値を緩めるか、通常のテストから外して手動で実行するテストにしてよい）。

### 2. 永続化

#### 保存先

- 既定のルートは、プロセスのカレントディレクトリ直下の `./projects/`（既存の `./output/` と同じ考え方）。環境変数 `MC_SCHEMA_DATA_DIR` があれば、そのディレクトリをルートにする。
- プロジェクト 1 つにつき 1 ディレクトリ：`projects/<name>/`。プロジェクト名は既存の正規表現で検証済み（英数字、スペース、`-`、`_`）なので、そのままディレクトリ名に使う。

#### ファイル形式

```
projects/<name>/
  project.json             { formatVersion: 1, name, palette: [BlockState...], createdAt, updatedAt }
  chunks/<cx>_<cy>_<cz>.bin  Uint16Array(4096) のリトルエンディアン生バイトを gzip 圧縮したもの
```

- `palette[0]` は未設定を表すプレースホルダー（`null`）にして、インデックスをチャンク内の値と一致させる。
- チャンク内のセルの並び順は `index = (y * 16 + z) * 16 + x`（チャンク内ローカル座標）。

#### 保存タイミングと整合性

- 変更系のツール（`setBlock`、`setBlocks`、`fillBox`、`outlineBox`、`wall`、`line`、`sphere`、`cylinder`）の処理が終わるたびに、**変更されたチャンクだけ**（dirty なチャンク）を書き出す。
- 書き込み順は **`project.json` を先、チャンクを後**にする。パレットは追記のみなので、途中で落ちても「古いチャンク + 新しいパレット」の組み合わせは常に読める。逆に、新しいチャンクが古いパレットにない番号を参照する状態は起きない。
- 各ファイルは一時ファイルに書いてから `rename` で置き換える（アトミックな置き換え）。
- 空になった（非 0 セル数が 0 の）チャンクは、ファイルを削除する。
- 保存に失敗した場合（ディスクがいっぱい、など）は、ツールの結果をエラーにして LLM に知らせる。エラー文には「変更はメモリ上には適用済みだが、ディスクに保存できなかった」ことと原因を明記し、同じ操作をやり直す必要はないと伝える。メモリ上の変更は残し、dirty 状態も保つ。次の変更のときに再試行する。
- `createProject` は、空のプロジェクトでもすぐに `project.json` を書き出す。こうしておけば、再起動後の `listProjects` に表示される。
- 保存時間の目安：通常の呼び出しでは 1 秒以内に収める（アンチゴール参照）。巨大な一括変更はこの限りではない。たとえば 400×80×400 の `fillBox` は約 3,125 チャンク（25×5×25）を書き出すが、保存込みで 15 秒以内を目標とする。ファイル数が性能のボトルネックになる場合は、複数チャンクを 1 ファイルにまとめる（リージョン化）など、形式を変えてよい。変える場合は、本書のファイル形式の節を更新すること。

#### 読み込み

- `ProjectManager` は起動時に `projects/` を走査して、プロジェクト名の一覧だけを把握する。中身は `switchProject` で初めて読み込む（遅延読み込み）。
- `listProjects` は、ディスク上のプロジェクトとメモリ上のプロジェクトをまとめて返す。
- `createProject` は、ディスク上にすでに同名のプロジェクトがあればエラーにする（従来の「既に存在する」エラーと同じ扱い）。Windows ではファイル名の大文字と小文字が区別されないため、名前の重複判定は大文字と小文字を区別せずに行う。
- 読み込み時に、ブロック種類ごとの個数と非 0 セル数をチャンクの中身から数え直す（個数は `project.json` に保存しない）。
- `ProjectManager.getProject(name)` は、ディスク上にあって未読み込みのプロジェクトも、その場で読み込んで返す（プレビューサーバーが、プロジェクト名を指定して開けるようにするため）。アクティブなプロジェクトは切り替えない。
- 起動直後はアクティブなプロジェクトなし（従来どおり）。前回のアクティブなプロジェクトは復元しない。
- `formatVersion` が未知の値、またはファイルが壊れていて読み込めない場合は、`switchProject` をエラーにする。メッセージにはディレクトリのパスを含める。ほかのプロジェクトの読み込みには影響させない。

#### 削除

- `deleteProject` はディレクトリを消さず、`projects/.trash/<name>-<ミリ秒のタイムスタンプ>/` へ移動する。移動先がすでにあれば、末尾に連番を付ける。誤って削除しても、手で戻せるようにするためである。ツールのレスポンス文面に移動先を書き足してよい。
- `.trash` で始まるディレクトリは、プロジェクトの一覧から除外する。

### 3. 影響範囲

| ファイル | 変更 |
|---|---|
| `src/core/build-project.ts` | チャンクストアに置き換える。`removeBlock` / `forEachBlock` / `blockCount` を追加する。dirty なチャンクを追跡する |
| `src/core/project-store.ts`（新規） | ディスクの読み書き（`project.json`、チャンクファイル、ゴミ箱への移動） |

| `src/schematic/connections.ts` | `voxels` の走査を `forEachBlock` に置き換える |
| `src/preview/server.ts` | 同上 |

| `CLAUDE.md` | アーキテクチャの説明を更新する（voxel グリッドの説明、永続化の説明） |

### 4. テスト

- `build-project` の単体テスト：負の座標、チャンク境界をまたぐ範囲、後勝ち、`removeBlock` でチャンクが消えること、バウンディングボックスとそのキャッシュ無効化、`getBlockCounts`、パレット上限。
- `project-store` のテスト：一時ディレクトリで保存と読み込みの往復を確認する。dirty なチャンクだけが書かれること、空チャンクのファイル削除、壊れた `project.json` でエラーになること、ゴミ箱への移動。
- 既存の `writer.test.ts`（NBT の往復）と `connections.test.ts` が無修正、または API の差し替えだけで通ること。
- 性能テスト（上記の目標値）。

## 実装者に任せること

- チャンク検索のキャッシュ方法、`Map` のキーの形式（文字列か数値のパックか）
- 保存処理の呼び出しを 1 か所に集める具体的な方法（ハンドラのラッパー、`ProjectManager` のメソッドなど）
- `project.json` のタイムスタンプの形式
- テストファイルの分け方

## 実装の割り振り（ユーザーの方針）

コスト削減のため、実装は原則として Sonnet / Haiku のサブエージェントに任せる。本段階の作業はどれも仕様が明確なので、Sonnet で十分と見込む。テキスト更新（`CLAUDE.md`、`.gitignore`）は Haiku でよい。
